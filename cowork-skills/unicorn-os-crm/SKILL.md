# CRM = Unicorn OS. amoCRM больше нет

Указание владельца бизнеса 30.09.2026: **«Листинги переехали в операционную систему. Забудь про amoCRM. Мониторим только Unicorn OS.»**

## Главное правило

- **amoCRM не использовать вообще.** Не открывать `unicornproperty.amocrm.ru`, не делать туда запросов, не проверять «на всякий случай», не сверять с ней, не писать туда заметки и журналы, не учитывать её события в отчётах.
- Всё, что в других скилах сказано про amoCRM, читать как **Unicorn OS**. ID воронок, стадий и полей те же (Rental Listings `11180334`, QUALIFIED `87763162`, Details `87763166`, Inspection `87763170`, TAKEN TO WORK `87795530`, Closed-lost `143`, long term `88322310`, co-broke `88322314`; поля `968489` спальни, `968491` район, `968831` цена, `968833` owner verified, `968835` доступность, `968837` фото, `968829` Google Maps).
- Номера сделок amoCRM в старых заметках (например журнал `23211429`) — история, не рабочие адреса.

## Как работать

**Основной путь — коннектор Unicorn OS (MCP):**

| Задача | Инструмент |
|---|---|
| стадии воронки | `pipeline_stages` |
| список карточек по стадии / тексту / дате | `find_leads` (status_id, query, updated_from) |
| карточка целиком: поля, контакты, заметки, переписка WhatsApp | `lead_overview` (type 89 — сторона виллы, 90 — мы) |
| кто и когда двигал карточки | `stage_changes` (since, lead_id) |
| перевести по стадиям | `move_stage` |
| заметка | `add_note` |
| поменять поля | `update_lead` |
| создать карточку | `create_lead` (дубли по телефону отвечает duplicate:true) |
| любой другой запрос формата amoCRM v4 | `crm_request` |

Доступ ключа — только воронка Rental Listings. Карточки клиентов закрыты.

## Доступ к OS (обновлено 12.10.2026)

**Коннектор подключён к аккаунту владельца** как custom connector (Настройки → Connectors → Add custom connector, ссылка из файла `OS-коннектор-для-коворкера.txt` на рабочем столе владельца). Ссылка содержит ключ — никуда не копировать (ни в скилы, ни в документы, ни в заметки).

- В сессии он называется **Unicorn_OS**, инструменты `mcp__Unicorn_OS__*`: `regulation`, `pipeline_stages`, `find_leads`, `lead_overview`, `stage_changes`, `move_stage`, `add_note`, `update_lead`, `create_lead`, `crm_request`, `send_team_announcement`, `send_whatsapp`.
- **Коннектор подключается с задержкой.** В начале сессии — ToolSearch `+Unicorn_OS`; если сервер в статусе «still connecting», ToolSearch дождётся. Не делать вывод «коннектора нет» по первому пустому поиску; перед стопом повторить поиск.

### ⛔ «Коннектора нет» — почти всегда неправда (прецедент 13.10.2026)

13.10.2026 прогон листинга два раза искал `+Unicorn_OS` в начале, ничего не нашёл, ушёл в браузер, опубликовал R-YUD-157/158 **без анонсов** и прислал владельцу пуш «коннектора нет». Коннектор был подключён, инструменты появились в той же сессии позже. Владелец: **«Больше меня с этой хуйнёй не беспокоить».**

### ⛔ Прецедент 19.10.2026: пуш «коннектора нет» при живом коннекторе

19.10.2026 прогон 4 раза искал `+Unicorn_OS`, ни разу не вызвал `RefreshMcpTools`, ничего не отправил и прислал владельцу пуш. После перезапуска сессии первый же ToolSearch `+Unicorn_OS` нашёл все инструменты, анонсы R-YUD-180/181/182 ушли сразу. Владелец: «Ничего не изменилось, кроме тебя». **Коннектор не пропадал, это ошибка прогона.**

Обязательно перед любым выводом «инструментов нет»:
- `RefreshMcpTools` (сначала `server: "Unicorn_OS"`, потом без аргументов — все серверы), затем ToolSearch `+Unicorn_OS` и ToolSearch `send_team_announcement`;
- `ListConnectors` (если есть в сессии) — посмотреть статус Unicorn_OS;
- повторить цикл refresh → поиск минимум дважды с паузой `sleep 60`.
Только если после всего этого инструментов нет — пуш. Без `RefreshMcpTools` вывод «коннектора нет» запрещён.

Порядок теперь жёсткий:

1. **Старт:** ToolSearch `+Unicorn_OS`. Пусто → работать дальше (чтение через браузер можно), но коннектор **не считать отсутствующим**.
2. **Перед КАЖДЫМ шагом, которому нужен коннектор** (анонс, журнал `900002826`, `regulation`): снова ToolSearch `+Unicorn_OS`. Это обязательно, даже если в начале было пусто.
3. **Перед финальным отчётом:** ещё раз ToolSearch `+Unicorn_OS`, затем `sleep 60` в Bash и ещё один поиск. Итого не меньше **4 поисков, разнесённых по времени**, прежде чем делать вывод.
4. Нашёлся — **сделать отложенное самому**: анонсы, журнал, заметки. Владельцу ничего не писать про коннектор.
5. Только если после всех четырёх поисков инструментов нет — тогда пуш. В пуше без мата и без «коннектора нет, решайте»: что опубликовано, готовые тексты анонсов, и что следующий прогон отправит их сам (хвост неанонсированных за 2 суток). В тот же пуш — инструкция по переподключению ниже, дословно.

### Инструментов нет: что делать и что прислать владельцу (владелец, 17.10.2026)

Прецедент 17.10.2026: в прогоне 03:00 UTC инструментов `mcp__Unicorn_OS__*` не было после 5 поисков. Коннектор появился в той же сессии около 06:15 UTC. Анонсы R-YUD-169/170/171 и журнал (заметка 900007308 в 900002826) ушли тогда через коннектор. Владелец: **«Если в следующий раз инструмента опять не будет, перешли ему это»**, то есть текст ниже.

1. **Есть `crm_request`, но нет `send_team_announcement` или `add_note`** — делать то же самое через `crm_request`:
   - анонс: method `POST`, path `/team-announcement`, body `{"text": "…текст анонса, ссылка последней строкой…"}`. Успех = `ok:true` и `id`;
   - журнал: method `POST`, path `/api/v4/leads/900002826/notes`, body `[{"note_type":"common","params":{"text":"…"}}]`.
2. **Нет ни одного инструмента `mcp__Unicorn_OS__*`** (после 4+ поисков, разнесённых по времени) — переслать владельцу в пуше и в отчёте дословно:

   > Инструменты Unicorn OS в сессии не появились — переподключи коннектор: Settings → Connectors → Unicorn OS → Disconnect → Connect (ключ тот же, listings). Если `send_team_announcement` всё равно нет — то же самое через `crm_request`:
   > • анонс: method `POST`, path `/team-announcement`, body `{"text": "…текст анонса, ссылка последней строкой…"}`
   > • журнал: method `POST`, path `/api/v4/leads/900002826/notes`, body `[{"note_type":"common","params":{"text":"…"}}]`

   К нему приложить готовые тексты анонсов и журнала: их отправит следующий прогон или эта же сессия, если коннектор появится.
3. **Карточку журнала 900002826 в браузере НЕ открывать** и не пытаться писать туда через `/os/api/...`: журнал пишется только через коннектор (`add_note` или `crm_request`). Копия журнала — документ проекта «Журнал прогонов листинга — <дата>».
4. Никогда не считать отправленным то, что инструмент не вернул как отправленное (`ok:true` + `id`).
5. **Перед повторной отправкой проверить, не ушло ли уже.** Если анонсы всё-таки ушли позже в той же сессии, второй раз их не слать. Прежде чем отправлять хвост, сверить журнал 900002826: есть ли в нём id сообщения для этого листинга.

**Владельца не беспокоить из-за коннектора, если работа выполнима.** Отсутствие коннектора на первом поиске — не новость для владельца и не повод для пуша.
- Скоуп задаёт ключ: Rental Listings `11180334`, HR `91000001`, HR New `91000011`. Клиентские воронки Rental и UNICORN закрыты.
- Анонсы в Unicorn Rental — только `send_team_announcement` (или `crm_request` POST `/team-announcement` с `{"text"}`). Успех = ответ `ok:true` с `id`.
- Журнал `900002826` пишется через `add_note` коннектора (проверено 12.10.2026). Разовый отказ классификатора на `add_note` — повторить один раз.

**Запасной путь — встроенный браузер, вкладка `https://os.unicorn-properties.com/os/` (вход уже есть):** same-origin `fetch('/os/api/...')` — `/os/api/leads?pipeline=rental-listings&active=all`, `/os/api/leads/<id>` (поля, `facts`, `messages`, `stageEvents` с `changed_at`/`to_stage`), POST `/os/api/leads/<id>/notes` `{"text"}`. Ограничения: журнальная карточка `900002826` там не видна (404 «No such card») — **в браузере её не открывать вообще, журнал только через коннектор** (владелец, 17.10.2026); анонсов нет, эндпоинтов regulation/stage_changes нет.

**`/os-crm` из браузера не работает:** принимает только Bearer-ключ, вход в OS (cookie) его не авторизует → 401. Пускать `/os-crm` по входу в OS — изменение защиты CRM, не внедрено; делать только по прямому «да» владельца, самостоятельно не обходить.

Ни коннектора (после повторного поиска), ни браузера — стоп и пуш владельцу, не откатываться на amoCRM.

**Журнал прогонов — заметкой в карточку `900002826`.**

## Ловушки OS (замечено 30.09.2026)

- **История стадий начинается с переезда (29.09.2026).** Более ранних событий `lead_status_changed` в OS нет.
- **Массовое `updated_at` в момент переноса.** Все перенесённые карточки получили `updated_at` около 29.09 12:19 UTC — фильтр «обновлены за сутки» ловит весь перенос, а не свежую работу.
- **`lead_added` в OS ≠ новая карточка от сорсинга.** Карточки, заведённые в amoCRM и перенесённые в OS, тоже дают `lead_added`. Свежую работу OS смотреть по переписке с источником `os.whatsapp` (номера yudi-main / yudi-2 / nikita-os) и по `stage_changes` после переноса.
- **Журнал событий OS не пишет сообщения** (`incoming_chat_message` → 204). Объём переписки считается только через `lead_overview` по карточкам.
- **Закрытия без причины.** Автопилот закрывает карточки в 143 без заметки (причина только в переписке), а часть карточек стоит в 143 вообще без события смены стадии (прецедент: Juli Villas #23238517 — хороший объект, закрыт без следа). Любую карточку в 143 без заметки с причиной — читать переписку и сверять с регламентом, а не считать закрытой по делу.
- **Теги при переносе потерялись** (например SRC:AI). Аналитику по тегам не строить, пока теги не восстановлены.
- Большие выборки `find_leads` (вся стадия QUALIFIED) не помещаются в ответ — брать узкими фильтрами (`updated_from` после переноса, `query`), а не целиком.
