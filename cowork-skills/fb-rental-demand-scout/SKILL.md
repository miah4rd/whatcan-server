> - **Бюджет ниже 40М/мес — лиды на Facebook не ищем вообще.** Бюджет = нижняя граница диапазона: «35–50М» = 35 → нет; «40–60М» → да; «до 50М» / «max 55М» → бюджет не подтверждён. Годовой ÷ 12 (480М/год = 40М → да; 450М/год → нет). Общий за период ÷ число месяцев. $1 ≈ 16 500 IDR.
> - **Срок меньше 6 месяцев — пропускаем**, даже при высоком бюджете: «1 месяц», «2–3 месяца», «1–4 месяца», «3–5 месяцев» → нет. Диапазон срока — по нижней границе («6–12 мес» → да; «3–6 мес» → нет). «Long term», «yearly», «1 year+» → да.
> - Спальни по нижней границе: 1BR, студии, «1–2BR» → нет; «2–3BR» → да.
> - Бюджет или срок не указан → карточку НЕ заводить. Можно написать (квота) и спросить бюджет, срок и WhatsApp; карточка — только после ответа, подтверждающего 2BR+, 40М+ и 6+ мес. Любая неоднозначность трактуется против лида.
> - Окно свежести для профиля 40М+/6+ мес — 14 дней (такие ищут неделями). Приоритет: бюджет/мес по убыванию → срок → спальни → свежесть.
> - В отчёте причины отклонения: посредник/агент, район вне наших, **срок меньше 6 мес**, **бюджет ниже 40М/мес или не подтверждён**, меньше 2 спален.
> - Гейт перед сообщением и карточкой: `ГЕЙТ: спальни = <N>; ≥2 — да/нет; бюджет = <нижняя граница>М; ≥40 — да/нет; срок = <мес>; ≥6 — да/нет; свежесть в окне — да/нет`. Хотя бы одно «нет» — ни сообщения, ни карточки.

Технические особенности встроенного браузера — известные факты, не диагностировать их заново каждый прогон:
- В `javascript_tool` **нет top-level await**. Писать через `.then()`. Конструкция `await fetch(...)` падает с SyntaxError.
- Возвращать из JS **только нужные поля собранной строкой**, а не сырой JSON или `res.text()`: сырой вывод режется фильтром с сообщением `[BLOCKED: Cookie/query string data]`.

- Основной способ чтения страниц — `get_page_text` / `read_page`. `computer{action:"screenshot"}` — когда нужна дата поста или проверка баннера лимита.
- Поиск по группе отдаёт ~5 результатов по релевантности и **не догружается скроллом**. Чтобы достать больше — менять формулировку запроса, а не листать выдачу.
- Лента группы виртуализирована: `innerText` отдаёт 1-2 поста независимо от скролла. Для ленты работать скриншотами либо целевыми запросами.
- Отправка сообщения в Messenger: сфокусировать композер через `document.querySelector('div[contenteditable="true"][aria-label="Write to <Имя>"]').focus()`, напечатать текст, затем нажать синюю кнопку отправки по координатам. Enter в композере не отправляет. Перед отправкой проверить поле «To:» — там должен быть ровно один получатель; случайный ввод в поле получателей добавляет лишних людей в тред.

## КВОТА — главное правило

- **1 исходящее в новый или холодный тред за один прогон. Не больше.**
- **5 исходящих за скользящие 24 часа.** Пять слотов по одному и есть дневная норма.
- Окно **скользящее, а не календарное**: сообщения вчерашнего вечера продолжают занимать квоту сегодня утром. Считать всегда по времени последних 24 часов, а не с полуночи.
- Follow-up тратит ту же квоту, что и холодный DM. Гипотеза «follow-up бесплатный» проверена и не подтвердилась.
- **Ответ в уже открытый живой тред квоту не тратит и лимитом не бьётся.** Дожимать тех, кто ответил, можно свободно даже при блоке.
- Не больше 1 follow-up на одного человека. Человек, получивший DM и один follow-up, исчерпан — писать ему третий раз нельзя.
- Каждое сообщение переписывается под конкретного человека. Copy-paste одного текста нескольким людям запрещён.
- Перед отправкой проверять лимит живьём: открыть `https://www.facebook.com/messages/t/<user_id>`, убедиться что поле ввода «Aa» активно и нет баннера. Если баннер «You've reached the message request limit» — лимит не обходить, зафиксировать дословно как артефакт внешнего отказа и остановить все исходящие до освобождения окна.
- Наш номер и ссылки wa.me не давать никому и нигде.
- Больше групп в списке не значит больше исходящих — квота не меняется. Расширенный список даёт (а) больше кандидатов с WhatsApp прямо в посте, которых можно заводить в CRM бесплатно без квоты, и (б) более широкий выбор для того единственного, кому пишем за слот.
- **Квота — потолок, а не план. Пустой слот по исходящему — допустимый исход.** Если нет кандидата, который проходит все проверки Шага 3, исходящее не отправляется вовсе. Заполнять слот пограничным кандидатом запрещено. Пустой слот по карточкам допустимым исходом НЕ является — см. гейт.

В отчёт каждого прогона писать состояние квоты в формате: `КВОТА: исходящих за прогон X из 1, за скользящие сутки Y из 5`.

## Шаг 2. Прогон групп

По каждой группе открывать `https://www.facebook.com/groups/<ID>/search/?q=looking%20for` и читать через `get_page_text`. Не тратить попытку на `javascript_tool` с селектором `div[role="article"]` — он не работает в текущей вёрстке FB, это известный факт.

Экономичный обход: `navigate` + `javascript_tool` складывать в один `browser_batch` по 2-3 группы за вызов, разворачивать «See more» и возвращать срез `document.body.innerText`.

Чтобы вытащить кандидатов с номером прямо из поста — прогонять по тексту страницы регулярку `/\+\d[\d\s\-().]{7,}|08\d{8,}|wa\.me\/\d+/g` и возвращать по 600-900 знаков контекста перед каждым совпадением. Это дешевле, чем читать выдачу целиком.

**Про даты и свежесть.** Выдача поиска ранжируется по релевантности, а НЕ по свежести — в первой пятёрке регулярно попадаются посты недельной давности. Переключатель «Recent posts» порядок не исправляет. В `get_page_text` даты чаще всего нечитаемы. **Рабочий способ:** `computer{action:"screenshot"}` страницы поиска — под именем автора дата видна открытым текстом. Дату финального кандидата обязательно проверять скриншотом перед отправкой сообщения. Если скриншот падает по таймауту «Browser pane is not displayed» — это временный сбой, повторить позже, отказом он не является. Дополнительные способы: целевой поиск по группе по уникальной фразе из текста поста; JS-фильтр по шаблонам меток времени.

Полный текст поста разворачивать одним вызовом:
`let n=0;[...document.querySelectorAll('div[role="button"],span')].forEach(e=>{if(e.innerText==='See more'){e.click();n++}});n`

user_id автора для Messenger:
`[...document.querySelectorAll('a[href*="/user/"]')].map(a=>a.innerText.trim()+' => '+a.href.split('?')[0]).filter(v=>v.length>4).filter((v,i,s)=>s.indexOf(v)===i).join('\n')`

## Шаг 3. Фильтр и выбор одного кандидата

**Район здесь НЕ ранжируется.** Не применять ранжирование районов из скилла `bali-demand-matrix` — оно относится к другой задаче.

Берём: аренда виллы/дома 2BR+ на срок от 6 месяцев (профиль 17.10), район из наших — Чангу (Батубулонг, Берава, Паданг Линьонг, Тибубенеанг, Падонан, Ума Булух, Бабакан), Переренан, Умалас, Керобокан, Семиньяк, Семер, Тумбак-Баюх, Мунггу, Сесех, Чемаги, Далунг.

**Бюджетная отсечка: от 40 млн IDR/месяц и выше (владелец, 17.10.2026).** Жёсткий порог квалификации. Действует и на исходящее, и **на заведение карточки тоже**. Кандидат ниже порога пропускается: ни карточки, ни сообщения, ни дожима. Бюджет не указан явно — карточку не заводить, можно только спросить бюджет и срок.

**Правило диапазонов.** Бюджет кандидата — это ОДНО число: нижняя граница заявленного диапазона. Проходит только кандидат, у которого ВЕСЬ диапазон от 40М и выше. «35–50М/мес» = 35М → НЕ проходит. «40–60М» → проходит. «До 50М» без нижней границы → считать «не указан явно». Годовой бюджет делить на 12 и применять то же правило: 450M/год = 37.5M/мес → нет; 480M/год = 40M/мес → да. **Любая неоднозначность бюджета трактуется ПРОТИВ отправки исходящего.**

**РАНЖИРОВАНИЕ ПО ЦЕННОСТИ СДЕЛКИ — главный критерий выбора.** Среди прошедших отсечку выбирать по `бюджет/мес (нижняя граница) × срок в месяцах` (год и дольше = 12, 6+ мес = 6, 3+ мес = 3, 1–2 мес = 2, срок не указан = 3). Долгосрочник с высоким чеком ВСЕГДА приоритетнее краткосрочника со свежим постом. Свежесть — тайбрейкер при сопоставимой ценности (в пределах ~1.5×), а не самостоятельный критерий.

**Окно свежести — двухуровневое.**
- Обычные кандидаты: 24–48 часов.
- Кандидаты высокой ценности (срок 6+ месяцев И бюджет 40М+/мес, либо ценность от ~300М): окно 14 дней. Таким запросам подходит мало объектов, люди с высоким чеком ищут неделями, а цена упущенной сделки на порядок выше цены одного сообщения из квоты.

**Механический гейт перед отправкой — обязательный шаг.** Непосредственно перед отправкой любого исходящего выписать одной строкой: `ГЕЙТ: спальни = <N>; ≥2 — да/нет; бюджет = <нижняя граница>М/мес; ≥40 — да/нет; срок = <мес>; ≥6 — да/нет; ценность = <бюджет × срок>М; свежесть в пределах окна класса (48ч обычный / 14д высокая ценность) — да/нет; в бэклоге нет кандидата с большей ценностью в своём окне — да/нет`. Все «да» — можно отправлять. Хотя бы одно «нет» — исходящее запрещено. Строка обязана попадать в отчёт дословно.

**Свежесть у сильного кандидата — не повод спускаться ниже по ценности.** Если у лучшего по ценности кандидата не удаётся подтвердить дату: дожать проверку — целевой поиск по уникальной фразе, пермалинк, кросспосты, JS-фильтр меток времени. Если дата не подтверждена — пропустить исходящее и оставить кандидата ПЕРВЫМ в бэклоге с пометкой «дата не подтверждена». Выбирать вместо него кандидата с меньшей ценностью запрещено.

Кандидатов ранжировать по ценности и писать **только лучшему** среди прошедших гейт. Остальных — в бэклог.

## Шаг 4. Контакт и карточка

Если WhatsApp указан прямо в посте — карточку заводить сразу, квота не тратится. **Это основной путь выполнения закона №1**, а не побочный улов: такие кандидаты ищутся целенаправленно в каждом прогоне.

Если «DM me» — открыть https://www.facebook.com/messages/t/<user_id>, нажать Continue, написать личное сообщение и попросить WhatsApp. Это тратит квоту. Карточка заводится ПОСЛЕ ответа с номером.

Стиль сообщения: обращение по имени, «this is Nick from Unicorn Property», пересказ его требований своими словами, одна честная зацепка по существу, просьба дать WhatsApp. Не длиннее 600 знаков. Без эмодзи, без рекламных штампов, не выдумывать объекты, которых нет в каталоге.

Дедуп перед сообщением и перед карточкой (только Unicorn OS):
- открыть тред в Messenger — если наше сообщение там уже есть, повторно не писать;
- `find_leads` pipeline_id 11119150, query = имя автора;
- `find_leads` pipeline_id 11119150, query = последние 9 цифр номера;
- дедуп-сет одним запросом: `find_leads` pipeline_id 11119150, query `FB Lead`.
- Если человек уже есть в OS с активной карточкой и снова постит — НЕ заводить дубль, а `add_note` в эту карточку на английском: «Still actively searching - posted again <дата> in <группа>» с новыми деталями.

Создание карточки (Unicorn OS, `create_lead`, тело /leads/complex):
- `name` `FB group – <Имя автора>`, `pipeline_id` 11119150, `status_id` 87301078, `responsible_user_id` 12919178 (Nick). **Без тега Amelia, не на Амелию.**
- `_embedded.contacts`: имя автора + телефон WhatsApp.
- `custom_fields_values` (заполнять все, лучшим приближением, не пустыми):
  - 956455 имя клиента (text) · 956451 источник = `Facebook group` / `Facebook Messenger` (text)
  - 956449 «Budget» (text) · 959041 «Number of Bedrooms» (text) · 959039 «Preferred Area or District» (text)
  - 968367 «Move-in Timeline» (text) · 968495 срок аренды (text) · 968369 заметка-запрос (text)
  - 968489 «Request: bedrooms» (numeric) · 968491 «Request: area» (text) · 968493 move-in (text) · 968497 «Request: budget (jt/mo)» (numeric, млн IDR)
- Ответ `duplicate:true` → карточку не создавать, `add_note` в найденную.
- Одна заметка `add_note`, ТОЛЬКО на английском, одной строкой:
  `Type: RENTAL. Source: <группа + ID + свежесть поста, либо Messenger inbound>. Request: <спальни, район, сроки, требования>. Budget: <сумма или not specified>. WhatsApp: <номер>`

**Проверка после создания.** Через ~35 секунд `lead_overview` по новому lead_id: карточка в pipeline 11119150, ответственный 12919178, контакт с номером привязан, тега Amelia нет. Если карточку закрыл гейт регламента Rental (бюджет ниже 25M, только Улувату/Убуд/Санур, нет WhatsApp на номере) — это решение регламента, не возвращать её руками и не считать закрытием закона №1.

Только после этой проверки карточка считается заведённой и закрывает закон №1.

Всё, что попадает в карточку, — только на английском.

## Шаг 5. Отчёт

Формат отчёта задаётся файлом `fb-rental-demand-scout-gate` и подчиняется Правилу единственного результата. Здесь только содержание:

- номер слота;
- чек-лист из 11 источников с цифрами по каждой строке (`кандидатов N / с номером M / новых K`) и перечень источников, добавленных сверх списка;
- состояние квоты в указанном формате и результат живой проверки лимита;
- кому написали + дословная строка ГЕЙТ из Шага 3, либо явное «исходящее не отправлено» с причиной;
- какие карточки завели, с ID сделок и контактов;
- **таблица всех номеров WhatsApp, встреченных за прогон**: номер, имя, исход (`заведён lead_id <id>` / `дубль, лид <id>` / `отклонён: <одна из четырёх причин>`);
- бэклог и лучший кандидат в очереди;
- обязательная само-проверка последней строкой по форме из гейта.

Отчёт пишется только при наличии `lead_id` либо при внешнем отказе с артефактом. Прогон без того и другого не отчитывается, а продолжается.

## Бэклог

Бэклог живёт от прогона к прогону и обновляется каждый слот. Правила ведения: сортировка по ценности сделки, у каждой записи фиксируются имя, user_id или группа, дата поста, спальни, район, срок, бюджет, способ связи и пометка о состоянии (например «дата не подтверждена», «исчерпан: DM + follow-up», «manual review — low budget»).

Записи старше 14 дней выпадают даже из расширенного окна высокой ценности и переносятся в архивную часть — их можно использовать только если у человека нашёлся более свежий кросспост.
