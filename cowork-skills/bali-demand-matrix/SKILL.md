# Спрос/предложение для поиска ЛИСТИНГОВ (supply), не лидов

**Только для задачи по листингам.** Для поиска арендаторов — `fb-rental-demand-scout`,
там район не ранжируется.

# ⛔⛔ МЕТОДИКА АНАЛИТИКИ И ТАРГЕТА НА ПОИСК (владелец, 25.09.2026)

Три шага, строго в этом порядке. Таблица — ОДНА, в этом формате, в каждом прогоне
и в каждом отчёте.

## Шаг 1. Рейтинг по спросу за 14 дней

Ячейка = спальни × район × бюджет (полосы lt30 / 30-50 / 50-80 / 80+ млн в месяц).
Отсортировать ячейки по числу заявок за 14 дней, по убыванию.
`% спроса = заявки ячейки / все размещённые заявки куба`.

## Шаг 2. Предложение на сегодня относительно спроса

Для каждой ячейки — число живых листингов (Supabase, свободны в ближайшие 3 месяца).
`% предложения = листинги ячейки / все живые листинги`.

## Шаг 3. Коэффициент = % спроса / % предложения

| кофф | значит | действие |
|---|---|---|
| **∞** (листингов 0) | спрос есть, предложить нечего | ищем |
| **> 1** | дефицит | ищем |
| **≈ 1** | баланс | не приоритет |
| **< 1** | перебор | **не ищем** |
| спрос 0, листинги есть | мёртвый сток | отдельной строкой владельцу |

## Приоритизация = таргет на поиск

1. Ячейки с 1-2 заявками за 14 дней — шум, в таргет не брать.
2. Из ячеек с коффом > 1 (включая ∞) идём **сверху вниз по рейтингу спроса**
   (шаг 1), а не по величине коффа. Сильный спрос окупается быстрее.
3. Сколько карточек в ячейку: `дефицит = % спроса × все листинги − листинги ячейки`,
   округлить, **потолок 4 на ячейку**.
4. Раздать дневную норму (20) сверху вниз. Остаток — следующим по рейтингу ячейкам
   с коффом > 1.
5. План дня фиксируется ЧИСЛАМИ по ячейкам ДО первого поискового запроса и пишется
   в журнал. Ячейки с коффом < 1 не искать, пока план не закрыт.

⛔ Прежний «индекс» (доля стока / доля спроса) = 1 / кофф. Где ниже по файлу сказано
«индекс» — читать через кофф: индекс < 1 = кофф > 1 (дефицит).

## Формат таблицы в отчёте

```
# | Ячейка | Спрос 14д | % спроса | Листингов | % предл. | Кофф | План
```
Плюс строки: перебор (кофф < 1), мёртвый сток (N из всех, %), качество разметки.

## Границы метода — проговаривать в отчёте

Кофф показывает раскладку портфеля относительно спроса, а не достаточность каталога.
Пропорциональность не учитывает оборачиваемость (годовой арендатор против помесячного).

# ⛔ ШЕСТЬ ПРАВИЛ, КОТОРЫЕ НАРУШАЛИСЬ

## 1. СЧИТАТЬ ПО ТРЁМ ОСЯМ СРАЗУ: СПАЛЬНИ × РАЙОН × БЮДЖЕТ

Одной оси мало, двух мало. Ячейка — всегда тройка. Признак, что шаг пропущен:
в таргете фигурирует район без указания спален и бюджетной полосы.

## 2. ИНДЕКС ПЕРЕСЧИТЫВАЕТСЯ В НАЧАЛЕ КАЖДОГО ПРОГОНА

Никогда не брать таргет из таблицы в этом файле. Любая таблица здесь — снимок
на дату. Ячейки переворачиваются за сутки.

Порядок обязательный: спрос за 14 дней → сток на сейчас → доли → индекс →
таргет дня → только потом сбор пинов.

## 3. В СПРОС ИДУТ ВСЕ ЛИДЫ ВОРОНКИ, ВКЛЮЧАЯ CLOSED LOST

Указание владельца 12.09.2026. Лид закрывается в Closed lost чаще всего тогда,
когда мы ничего не смогли предложить. Отфильтровав их, мы вычёркиваем ровно те
запросы, по которым у нас дыра в каталоге. Замкнутый круг.

Единственное, что не кладётся в куб — заявка без одного из трёх полей. Такие
считать и выводить отдельно: это метрика качества бота, а не спроса.

## 4. МУНГГУ — ОТДЕЛЬНЫЙ РАЙОН

Мунггу, Сесех и Чемаги считать раздельно. При этом спрос часто приходит
помеченный как «Сесех», а объекты стоят в Мунггу и Чемаги — это один пляжный
пояс. В таргете и в карточке писать «пояс Сесеха» с указанием фактического пина
во FLAGS. Тумбак-Баю в пояс не входит.

## 5. МНОГОРАЙОННАЯ ЗАЯВКА КЛАДЁТСЯ В КАЖДУЮ НАЗВАННУЮ ЯЧЕЙКУ

Больше половины заявок называют 2-5 районов сразу. Клиент готов взять любой,
значит это реальный спрос в каждом. Класть только в первый — занижать остальные.

## 6. КАЧЕСТВО РАЗМЕТКИ — ЧЕТЫРЕ ЧИСЛА В КАЖДЫЙ ОТЧЁТ

Сколько лидов за окно / сколько легло в куб / сколько неполных / сколько не наши
районы и `other`.

Замер 19.09 на 14 днях: 132 / 86 / 17 неполных / 12 не наши / 17 `other`.
Потеря на разметке 35% — та же величина, что и месяц назад. Семнадцать `other`
за две недели это отдельная задача к боту, а не шум.

## Как считать

### Спрос — amoCRM, воронка RENTAL, 14 дней, ВСЕ статусы

`pipeline_id 11119150`. Только `fetch` из вкладки, открытой на
`unicornproperty.amocrm.ru` — прямой запрос к `api-b.amocrm.ru` режет CORS.

```
GET /api/v4/leads?limit=250&page=N&filter[pipeline_id]=11119150
    &filter[created_at][from]=<now - 14*86400>
```

⛔ Не добавлять `with=contacts` — запрос падает. Ретрай с паузой 2 с.

Поля — фолбэк по группам синонимов, брать первое заполненное:
- Спальни: 968489, 512421, 959041, 930557
- Район: 968491, 959039, 956457, 512215, 930561
- Бюджет: 968497, 956449, 755371, 539057, 921063, 930669, 877631
- Источник (для отчёта): 956451

Нормализация обязательна:
- Batu Bolong / Batubolong / Padang Linjong / Tibubeneng / Babakan / Uma Buluh /
  Echo Beach → Canggu; Semer → Kerobokan; Berawa, Munggu, Seseh, Cemagi,
  Tumbak Bayuh, Padonan, Pererenan, Umalas — каждый отдельно.
- Поле района часто содержит список через запятую — разбирать и класть заявку
  в КАЖДЫЙ наш район из него.
- Бюджет приходит как «45», «45jt», «45.000.000», «Rp 30-50 million»:
  словесный диапазон брать как есть, иначе первое число ≥ 1 000 000 делить на
  миллион, иначе первое в диапазоне 1000-100000 делить на тысячу.
- Заявку без любого из трёх полей в куб не класть, но посчитать.

### Предложение — Supabase, снимок на сейчас

Через `execute_sql` коннектора `Supabase`, проект `zveamkyyzfztzppwavws`.

```sql
SELECT p.area, p.bedrooms,
  CASE WHEN p.monthly_price_idr < 30000000 THEN 'lt30'
       WHEN p.monthly_price_idr <= 50000000 THEN 'b30_50'
       WHEN p.monthly_price_idr <= 80000000 THEN 'c50_80'
       ELSE 'd80plus' END AS band,
  count(*) AS n
FROM properties p
LEFT JOIN property_availability pa ON pa.property_id = p.id
WHERE p.listing_type='rent' AND p.is_draft=false
  AND p.area NOT IN ('Uluwatu','Tabanan','Balangan','Ubud','Sanur','Denpasar')
  AND COALESCE(
    CASE WHEN pa.status IN ('rented','occupied') THEN pa.end_date
         WHEN pa.status='available' THEN pa.start_date
         ELSE CURRENT_DATE END, CURRENT_DATE) <= CURRENT_DATE + interval '3 months'
GROUP BY 1,2,3 ORDER BY 2,3,1
```

Освобождается позже трёх месяцев — считать занятым. Отсутствие строки
в `property_availability` = «available now». Предложение окном не режется.
